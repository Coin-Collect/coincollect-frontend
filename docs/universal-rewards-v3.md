# Universal Rewards V3

## Architecture decision

V3 runs alongside V2 on Polygon (137). `UniversalRewards` owns the pool ledger and creates numbered pools without a per-pool deployment. It never transfers or approves an ERC-721. `RewardSwapAdapter` supplies price observation and restricted router execution. `FinalizedOwnershipVerifier` is an isolated-test contract that adds Base and Arbitrum identity verification to the same ledger. Treasury Vault holds available deposits and Reward Route Planner chooses approved swap paths. Polygon pools share a single ledger deployment.

## Settlement and ownership

`poolId` is global to the settlement deployment. The NFT identity is `keccak256(abi.encode(sourceChainId, collection, tokenId))`. Exposure and earnings are kept per pool and NFT identity. A wallet claim requires the current ERC-721 owner on Polygon, pays that owner directly, and never moves the NFT. ERC-721 approvals cannot authorize a withdrawal. ERC-1155 is deferred because semi-fungible ownership requires a different quantity and ownership-transfer model.

The frontend reads `CLAIM_PERIOD` from the verified ledger before displaying a deadline or enabling expiry recovery. Older immutable ledgers retain the claim rules in their deployed bytecode.

For normal Polygon transfers, the ledger reads `ownerOf` from the configured ERC-721 contract in the settlement transaction. Accrued value follows the token even if its new owner cannot retain a participation slot. The current owner can claim until `pool.end + 30 days`. A burned token has no live recipient, so its accrued balance remains in the pool until treasury settlement. Enrollment history remains addressable through bounded on-chain pages after an NFT leaves or loses its seat. ERC-721 Enumerable collections can list the connected wallet's eligible NFTs. Other collections can verify token IDs individually.

An ordinary ERC-721 provides no universal transfer notification. In V3.2, checkpoint updates the reward indexes using recorded participant addresses and total NFT power. Anyone can reconcile up to 32 specific positions per transaction to update counts and caps. Positions are processed in supplied order. Each old seat is released before evaluating the new owner's limits. If the new owner is over a cap, the active seat is released and vested credit remains with the NFT. The current owner can re-enroll when a slot opens. Claims check live ownership regardless of reconciliation.

The FarmCard displays a verified claimable balance and labels its interpolated live estimate. The estimate is bounded by recent on-chain data, available reserves and pool end. The counter can be paused and respects reduced motion. Harvest uses verified claimable positions. Large wallets can browse and select positions page by page, and an owner who received an NFT can look it up by collection and token ID. Pool details show recorded participant wallets, active NFTs and total power.

### Cross-chain guarantees

Base (8453) and Arbitrum One (42161) can participate in the same isolated logical pool. The witness helper reads two or more distinct HTTPS endpoints at the lowest finalized height they agree on. It requires a common block hash and timestamp, uses canonical block-hash calls for ERC-721 capability and `ownerOf`, and refuses disagreement or stale source data. The on-chain verifier accepts threshold EIP-712 signatures from distinct configured witnesses. The signed statement binds the source chain, NFT identity, finalized height, block hash, source and issue timestamps, observed owner, expiry, settlement chain, and verifier address. A source block can only advance. A new observation supersedes the old owner, even if the former certificate had time remaining. A certificate has a maximum 20-minute lifetime and the source policy further bounds its age. [EIP-712](https://eips.ethereum.org/EIPS/eip-712), [EIP-1898](https://eips.ethereum.org/EIPS/eip-1898), [Base finality](https://docs.base.org/specifications/transactions/transaction-finality), [Arbitrum finality](https://docs.arbitrum.io/how-arbitrum-works/reference/finality-and-reorgs)

The verifier can only deploy on chain 31337. The ledger also rejects a verifier on Polygon and rejects remote collections when no verifier is configured. Existing remote credit stays reserved when a proof expires. Accrual for that NFT stops at certificate expiry. V3.2 advances reward indexes up to each due certificate expiry, then updates remote seat weight and thresholds. Only isolated test pools use the bounded remote roster. A fresh certificate can restore a claim after pool end while the 30-day window is open. Wallet and NFT caps apply across all source chains in the same pool. The isolated model trusts the witness quorum and their finalized RPC evidence. A transfer after proof creation can remain invisible until a successor certificate arrives or the certificate expires. Production requires a reviewed source-side authorization design with explicit transfer and message-delay guarantees.

## Economics and balances

Each reward token has an independent cap in that token's base units. USD-equivalent estimates are display values only. For a timestamp clamped to the pool window, cumulative scheduled emission is `floor(cap × precision × elapsed / duration)`. Each interval uses the difference between cumulative scheduled values. Its maximum emission is multiplied by `min(activeWallets, threshold) / threshold`, with a zero threshold meaning full rate for any nonempty roster. After that it is bounded by uncommitted funded inventory. V3.2 divides scaled interval emission by total power and increases a separate index for each token. Each NFT accrues its power multiplied by the change in index, realized on demand. Division dust stays uncommitted and is smaller than total power in scaled subunits per token and checkpoint. No recent funding can retroactively finance an interval that already elapsed.

Credits are tracked at 18 extra decimal places over a token's base units. Payouts round down at the ERC-20 boundary. An NFT's fractional remainder carries between accruals and claims until the pool ends, when any remainder below one base unit becomes recoverable after the associated final claim. Empty, underfunded or below-threshold intervals do not grant a catch-up allocation. Accrual ends at `pool.end`. Until the deadline, anyone can return uncommitted funds to the immutable treasury and the current NFT owner can claim, including one ERC-20 independently if another token blocks a combined payout. At `pool.end + 30 days`, claims and reward-paying exits expire. Leaving without payment remains available. Anyone can send the remaining inventory to the immutable treasury one token at a time. Studio shows aggregate reserved credit, which includes fractions below the per-NFT payout unit, and each token's recovery status.

## Funding and automation

V3.2 uses the same CoinCollect admin wallet for Pool Studio, Treasury Vault and route governance. Treasury Studio shows available funds and the ledger's reserved pool allocations separately. An operator can select Treasury funding when reviewing a pool. The same transaction creates the pool and reserves the lifetime budget. Automatic mode tries a verified consolidated purchase first and uses bounded adaptive windows if the full allocation is too large for a safe route. Wallet-funded pools remain available.

The on-chain route planner allows an approved direct path or two approved hops through an allowlisted asset. Each hop reuses the adapter's router and pair checks and TWAP protections. Detailed route errors in Studio identify unavailable pairs, stale observations, reserve and price deviation limits. The worker estimates purchase gas in POL before sending. Treasury purchases are limited to 0.25 POL or 5% of the same input's protected POL equivalent, whichever is lower. Purchases without a verified POL valuation wait. The Treasury owner or operator can inspect confirmed spend separately from the worker's POL fees.

At pool end the worker returns unspent Treasury funding. At claim expiry it transfers remaining reward inventory back to the vault. The vault credits each recovered token to available funds. If a token transfer fails, others can still settle. Paginated pool liabilities in Treasury are read from the ledger and transaction history shows confirmed events in the last 2,000 blocks.

Production execution is disabled by default. An independently authorized Polygon configuration would require `COINCOLLECT_V3_AUTOMATION=polygon`, `COINCOLLECT_V3_ENABLE_POLYGON_EXECUTION=1`, a verified V3.2 settlement address and runtime hash, and server-only `COINCOLLECT_V3_EXECUTOR_RPC`, `COINCOLLECT_V3_EXECUTOR_ADDRESS`, `COINCOLLECT_V3_EXECUTOR_KEY` and `CRON_SECRET`. The executor must be distinct from the CoinCollect admin and every adapter governor. Keep only gas in its wallet. The code ships without a production schedule or executor credentials.

Each pool has one funding asset. Native POL wraps to WPOL before entering the same accounting. Per-token percentages allocate the funding budget in its original units. The operator uses Studio to preview and create the pool and funding rules atomically. The reward-token cap derives from the funding split and the checked minimum output of a representative interval. Studio's optional USD reference uses a supplied unit price and the pool duration. The reserve uses actual deposited and purchased quantities, and the divider between funding and rewards is on chain. ERC-20 deposits use an exact allowance when approval is needed.

Replenishment opens at most one purchase per pool, output token and epoch. The ledger verifies the requested epoch, allocation balance, funding window and available reward inventory before swapping. The transaction never sells committed rewards. A direct same-asset allocation moves budget accounting without a swap. Cross-asset swaps require a pinned CoinCollect router and pair code hash, minimum input/output reserves, a 30-minute minimum cumulative-price observation, a two-hour maximum usable price age, at most 50 basis points of input reserve per trade, and a deadline at most five minutes away. A two-sided spot check and the higher of TWAP, router and caller minimums bound price and execution. The ledger and adapter clear allowances and verify actual asset deltas. Reverts leave balances and the epoch marker intact.

The Vercel-compatible `/api/v3/replenish` endpoint authorizes the cron header and selects a bounded cycle of pools. It can refresh due pair observations and verifies replenishment against the exact `Replenished` event. For expired pools on a deadline-enabled ledger, it recovers each token independently and checks the matching `ExpiredRewardsRecovered` event. If receipt status is uncertain, it returns the submitted hash. The ledger's epoch marker and reward inventory make retries safe without a job database. This deployment profile allows the loopback Anvil executor on chain 31337. Hosted execution requires a separate authorized configuration. [Vercel Cron authorization and delivery](https://vercel.com/docs/schedules/cron-jobs/manage-cron-jobs)

## Before real assets can be used

1. Independently review the ledger, exact token list, collection trust, reward solvency, end-of-pool recovery, and swap protections. Confirm the accepted code hashes and storage invariants against reviewed builds.
2. Assign the same approved CoinCollect admin wallet to ledger administration, treasury ownership and route governance. Use a new versioned ledger for V3.2. Existing deployments retain their addresses and rules. Supply the allowed assets and actual WPOL address at deployment. Verify the router and each allowed direct pair against a fresh Polygon block, realistic order sizes, minimum reserves, and observable price history. Leave unsupported pairs disabled.
3. Approve and deploy a gas-only execution path with no treasury token authority. Approve the RPC, schedule, timeout, receipt monitoring, route pause and recovery runbooks. Set production Vercel secrets and schedule only after explicit authorization. Cron cadence and duration must fit the Vercel plan. Polygon gas is required for pool changes, oracle observations, replenishment, and claims. A paid RPC or external database is optional for the isolated design. [Vercel cron usage and pricing](https://vercel.com/docs/schedules/cron-jobs/usage-and-pricing)
4. Leave Base and Arbitrum payouts disabled until an independent review approves source authorization, finality verification, transfer race handling, witness controls, and recovery. A working isolated quorum test supplies no production authorization.

## Editing a published pool's presentation

Open Pool Studio V3 with the CoinCollect admin wallet. Use **Manage** to preview an existing pool, edit its name, artwork and description, or open its funding controls. The operator signs a message to save changes on the local fork. The local registry is shared by browsers on that preview and scoped by fork session and ledger configuration.

For Polygon, download a pool's presentation entry and merge it by `poolId` into `v3-pools.json` in the CoinCollect metadata repository. Preserve the entries for other pools. The document uses `{ "schemaVersion": 1, "chainId": 137, "ledger": "<lowercase ledger address>", "pools": [...] }`. Publish the reviewed document at `https://metadata.coincollect.org/v3-pools.json`, with CORS enabled for the CoinCollect frontend. An entry contains `poolId` as a decimal string, `name`, `description` and optional `artwork`. The catalogue and detail page read it independently of the pool state. The creation-time presentation remains the fallback. Schedule, reward caps, NFT rules and funding come from the verified ledger.

Studio pre-fills the remaining budget. The **Fund** action sequences an exact ERC-20 approval when needed and the deposit. The wallet confirms each transaction independently. A funded budget is allocated to the reward reserves by the worker as each funding window becomes eligible. Manual purchase, pause and recovery actions are under **Advanced funding controls**.

For a local preview running with `COINCOLLECT_V3_AUTOMATION=isolated`, keep `node scripts/run-v3-local-automation.cjs` running with the same `CRON_SECRET` and its loopback `V3_LOCAL_PREVIEW` URL. The worker checks every 30 seconds with the local test executor and continues when the Studio tab is closed. `COINCOLLECT_V3_AUTOMATION_FIRST_POOL` optionally sets the lowest pool ID to process. Hosted execution requires a separate deployment configuration.
